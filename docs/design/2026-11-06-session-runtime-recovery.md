# 会话运行状态恢复变更说明

日期：2026-11-06

状态：已实施并完成静态检查、子代理代码复核，运行时验收待执行。原始状态丢失的具体触发时序仍未实际复现。

## 目标与问题

任务在后台执行期间，用户可以切换到任意页面。返回会话后，页面应正确展示后台任务状态、消息和工具执行过程，并提供与实际状态一致的补充要求及停止入口。

本次现象是：页面允许提交“继续”，后端返回“已有任务正在运行，请先取消或等待结束”，同时顶部显示“会话连接异常”。问题在于前端展示和提交决策与后台状态不一致。

## 已确认事实与证据边界

- `src/stores/session.ts` 已在应用级 Map 中保存各会话 runtime；再次打开已初始化会话会直接复用。
- `src/features/chat/ChatPage.vue` 离开页面时保存草稿，卸载时清理页面定时器，不关闭后台任务。普通路由切换已经具备保留任务的机制。
- `src/services/pi/sessionRuntime.ts` 的 `open` 恢复历史、模型与 generation，但没有恢复后台活动任务状态或重新订阅已有进程。
- `src-tauri/src/pi/bridge.rs` 的 `start_mod_task_blocking` 检查现有进程活动、压缩或任务 running 状态，命中后拒绝新任务。
- 当前 `connect_pi` 拒绝忙碌会话，其连接路径会创建进程，不能直接作为运行中任务的订阅恢复接口。
- 当前“重新连接”经 `openSession` 调用 store 的 `open`，已初始化会话会提前返回，不能保证真正恢复事件接收。
- `client.ts` 的提交响应超时会使提交状态进入失败，但超时不能证明后台任务未启动或已结束。
- 本地日志中，与截图快照 `a18a9f63` 对应的旧任务在 2026-11-06 16:01—16:02 仍有执行记录。工具命令失败不等于整轮任务结束。

尚未确认前端活动状态具体在哪个时序丢失，不能将普通页面切换、热更新或页面刷新认定为本次已证实的触发原因。实施前应核对提交响应、活动事件、前端状态重建和后端任务状态的时序，避免仅补恢复入口而遗漏原始状态转换问题。

## 范围与约束

- 保留现有应用级 runtime 和页面自由切换机制。
- 补齐已有运行时的附着、状态恢复、断开期间内容恢复及提交异常后的状态核对。
- 区分连接恢复失败、任务提交失败和模型配置错误。
- 不因页面切换或恢复订阅而取消、重启后台任务；不自动重新发送用户输入。
- 不新增依赖，不修改任务业务规则、源码操作权限或安全边界，不重构无关模块。
- 用户已授权本方案通过对抗审核后实施；测试和启动应用仍须另行明确授权。

## 预期行为

| 场景 | 页面行为 |
| --- | --- |
| 运行中切换到其他页面再返回 | 继续展示同一任务的状态、消息和执行过程；保留停止入口 |
| 离开页面期间任务结束 | 返回后展示终态，不继续显示运行中 |
| 前端状态重建，后端进程仍存在 | 先恢复订阅和后台状态，再决定可用操作 |
| 后台运行且允许接收引导 | 补充要求走现有 `steer`，不创建新任务 |
| 后台正在准备、停止或压缩 | 显示对应状态，操作遵循现有保护条件，保留输入 |
| 后台确认空闲且不存在未确认提交 | 允许创建新任务 |
| 提交超时或后端拒绝占用 | 核对后台状态，保留输入，不自动重发 |
| 超时请求已被接收且任务已经结束 | 恢复对应任务终态和结果，不作为未执行需求提示重试 |
| 无法确认后台状态 | 显示状态确认失败及重试入口，暂不允许重复启动任务 |

应用完整重启时沿用已有任务中断处理，不恢复已终止的进程，也不重放输入。只读及归档会话继续遵循现有查看限制。

## 变更设计

### 恢复路径与参考项目

区分以下三条路径，不在每次返回会话时执行完整恢复：

1. **正常切页返回**：原 runtime 和订阅健康时只复用持续更新的状态，不清空消息、不重新载入整份历史。可查询后台运行快照核对状态，但不重新绑定通道。核对期间保留现有内容，并暂缓启动新任务；查询结果通过顺序边界与后续事件归并，不能覆盖查询期间收到的终态。重复核对合并执行。
2. **异常恢复**：首次打开已有会话、前端状态重建、订阅丢失或显式重新连接时，执行下文 attach、历史补齐和事件接续。健康状态须以当前 runtime 的有效订阅及接收状态判断，不能仅凭 initialized 或缓存的 online 标记。
3. **提交结果不确定**：按原 requestId 查询接收结果与任务状态；订阅健康时无需重新 attach，也不重载整份历史。仅在确认订阅异常时组合执行异常恢复；请求核对与当前运行快照分别处理。

参考 Orbit 固定提交 `8ee98d6816854405f8187a53a40e5471505fe2d8`：其 [rpc.ts](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/src/lib/rpc.ts#L316-L341) 在 `activateConnection` 复用连接快照并查询状态，在 `loadMessages` 读取消息后通过 `get_state` 的 `isStreaming`、`isCompacting` 恢复运行标记。借鉴其应用级连接状态和切换展示方式，不迁移 React 状态架构。其本地 `pi_connect` 会停止同 ID 旧进程，不作为本方案无副作用 attach 的实现依据；请求接收结果核对是本项目的额外约束。

### 1. 附着已有运行时并返回状态

新增语义明确的 attach 入口，与创建或重建进程的连接操作分开。attach 根据项目和会话查找已有运行时，在同一运行时锁的保护下绑定事件接收方并捕获状态。

返回状态应足以恢复：会话身份、当前 generation、活动任务上下文、准备／运行／停止／压缩状态、任务开始时间，以及是否存在可连接进程。无进程、进程空闲和任务运行中必须可区分，不能将“未找到进程”解释为“任务正在运行”。状态以实时运行时为依据，任务持久化记录用于历史和核对，不能单独替代进程状态。

存在未确认提交时，核对请求必须携带原始 requestId，返回该请求的接收结果、关联 taskId 及当前或最终状态，不能只返回当前活动任务。请求关联需在任务结束后仍可查询，并能被重建后的前端识别；实施时补齐现有任务记录缺失的请求关联，不通过消息正文或提交时间猜测。只有后端已明确拒绝，或已确认该请求不会再被接收执行，才返回“未接收”；查询时暂未发现记录不能据此排除仍在途的提交。

附着保持 taskId 和 generation，不调用 `spawn`、`stop` 或提交 prompt。运行中的任务不应因订阅恢复重新执行模型配置校验或被替换。

### 2. 保证恢复过程的一致性

恢复必须覆盖“读取历史—捕获快照—接收实时事件”之间的间隙：

1. 开始恢复时缓存新通道事件。
2. 后端在受保护的时点建立订阅并取得快照，定义可用于衔接历史与实时事件的边界。
3. 读取并恢复该边界之前的消息和执行记录，包括未完成工具的状态。
4. 应用快照后，按顺序归并缓存事件；重复消息和工具结果使用稳定标识去重。
5. 恢复完成后进入正常事件处理。

实施时需核对现有事件、历史和工具结果是否具备足够的稳定标识及顺序信息，选择范围最小的衔接方式。不能只用 generation 去重：同一代次内同样会产生多条状态及消息事件。不能让较早快照覆盖已经收到的结束事件。

同一会话的恢复请求由应用级 runtime 串行执行；重复点击复用进行中的恢复，不再发起第二个 attach。若发生前端状态重建或其他来源导致并发 attach，后端必须校验订阅批次：以服务端认可的订阅身份和顺序拒绝过期绑定，不能仅使用会在前端重建后归零的本地计数。旧 attach 即使最后取得运行时锁，也不能覆盖已确认的新订阅。响应与事件携带订阅身份，前端只接收当前有效订阅。

后端所有事件发送路径均须遵循当前订阅归属。现有异步差异刷新及准备状态会保存 channel 克隆，实施时必须一并处理：通过当前订阅目标转发，或将发往旧通道的事件完整纳入恢复边界的补齐范围，不能只替换 `process.channel`。验收应确认恢复前启动的异步操作仍能更新新订阅。

切换会话后，旧会话结果只能更新对应 runtime，不能覆盖当前展示对象。旧通道的迟到事件应按会话身份、代次和订阅身份隔离。前端丢弃旧结果不能代替后端防止旧订阅覆盖新订阅。

### 3. store 提供显式恢复动作

保留正常 `open` 对已初始化 runtime 的复用行为，增加显式恢复动作供“重新连接”、前端状态重建及状态核对使用。

恢复完成前显示同步状态，阻止创建新任务；恢复后一次性更新任务上下文、运行状态及停止／引导能力。开始时间沿用后台任务时间，不能从重新进入页面的时刻重新计时。

普通页面切换按“正常切页返回”路径只选择展示对象，不解绑后台任务，不调用历史恢复。前端状态重建后，打开已有会话应执行异常恢复，不能依靠新 runtime 的默认空闲值决定提交入口。

### 4. 提交失败后核对真实状态

占用拒绝、提交超时和响应未确认均按原始 requestId 核对接收结果与关联任务，并与当前运行快照分别处理：

- 后端明确本次请求未被接收，旧任务仍运行：恢复旧任务展示，恢复本次可编辑输入，不自动转发成引导；操作仍遵循旧任务的运行限制。
- 后端确认本次请求已被接收且任务仍在准备、运行或停止：恢复关联任务，消除本次提交的错误失败标记，避免重复发送。
- 后端确认本次请求已被接收且任务已完成、失败或取消：恢复对应终态、结果或错误，将本地未知占位关联为已确认历史，不将该请求作为未执行需求提示重试。
- 后端明确本次请求未被接收，且当前会话空闲：恢复可编辑输入和提交失败原因，允许用户再次提交。
- 接收结果未知或核对失败：保留“不确定／同步失败”，即使当前后台空闲也不能据此认定请求未执行，暂不允许重复提交该输入。

未确认提交包包含原始 requestId、所属项目与会话、原始文本、图片附件、文本附件及本地消息占位，由原 runtime 保留，核对完成前不能因超时、页面切换或历史恢复删除。新增草稿不能被旧提交的恢复结果覆盖；恢复被拒绝的输入时按提交快照与草稿版本判断，发生冲突则保留独立的可恢复提交内容。

历史恢复必须合并本地未确认提交包：已接收后依据 requestId 与历史关联并消除重复占位，明确拒绝后恢复编辑内容，未知时继续保留包和未知占位。调整当前发送前移除附件、超时不恢复以及 `finish(false)` 清理草稿的路径，避免恢复历史后丢失唯一副本。

页面切换期间，提交包仍归原 runtime；前端状态重建的支持范围必须包含恢复所需的请求身份与未确认内容。实施时优先复用现有草稿和本地提交恢复机制；若需新增本地存储，另行明确数据格式和清理时机，只保存未确认提交所必需的内容，不扩展为长期附件库。不确定状态不得通过清空草稿或丢弃附件结束。

不能通过文案匹配作为长期接口契约；实施时为占用、状态不确定及连接错误提供可区分的结果，保留对用户可读的说明。

### 5. 错误展示与重连

任务占用拒绝展示在本次提交或输入区，不作为连接故障。连接错误、提交错误和模型错误分别维护，成功恢复订阅仅清除对应连接错误。

“重新连接”调用显式恢复动作，不再通过普通 `open` 的复用分支假定连接已恢复。恢复失败保留输入和已有消息，并提供重试；不自动重启进程。

## 本次实现落点

- `reserve_pi_subscription` 为当前进程分配恢复票据，`read_pi_runtime` 在槽锁内校验代次和票据，返回快照并绑定新通道。健康查询同一接口但不附着、不读取历史。
- `Subscription` 的 clone 共享当前接收目标、订阅身份和事件序号，异步差异刷新及准备操作不再持有独立旧目标。内存只保留消息的累计版本和每个工具的最新执行记录；完整恢复在槽锁内读取历史并合并内存投影，以快照序号为后续事件边界。
- 第 11 版数据库迁移新增 `submission_requests`，提交登记先于后台准备，任务创建事务绑定 taskId。没有查询到记录仍为未知；请求登记后被明确拒绝才允许恢复重试。已绑定任务的失败原因保留在请求结果中。会话删除通过外键级联清理请求记录。
- IndexedDB `gen-mod-pending-submissions` 的 `submissions` store 按项目／会话保存尚未确认提交，包含 requestId、原始文本及附件；不保存凭据。正式用户消息确认后清理；明确拒绝可恢复编辑；已接收但未形成正式消息的内容由用户查看结果后关闭保留提示。清理在事务内核对 requestId，避免旧回调删除新提交。未知提交不按时间自动清理。
- `client.synchronize` 合并同一 runtime 的并发恢复；代次推进仅在新代次首次出现时重置订阅游标，旧代次事件先过滤再处理序号。健康查询的状态边界与正文接收游标分开：快照之前仍在途的正文和工具记录继续归并，旧生命周期不能覆盖快照。完整 attach 才按快照边界跳过已恢复内容。正常切页不清空正文、不重载历史；发现订阅身份改变时转异常附着。
- 无进程快照返回该会话最新持久任务的终态和结束时间，前端据此清理未结束的工具、思考及活动状态，不将无进程推断为成功；健康查询保留原通道身份，以接收仍在途的退出事件。
- `ChatPage` 将连接错误与其他操作提示区分；重新连接调用显式恢复，任务忙碌本身不阻止附着。未确认输入独立展示，恢复编辑时保护新草稿。

以下均为待执行验收，不代表已经通过。测试及启动应用须获得用户明确授权。

| 场景 | 验收标准 |
| --- | --- |
| 任务执行时切换项目页、设置页及其他会话后返回 | 原任务未重启或取消；状态和执行过程正确，各会话互不串台 |

| 订阅健康但提交响应不确定 | 仅核对原请求结果，不因提交超时重建连接或重复载入历史 |
| 离开期间正常完成、失败或取消 | 返回后状态与后台一致，保留错误或停止结果 |
| 前端状态重建，后台继续执行 | 恢复同一 taskId 和 generation，消息与工具结果无缺失或重复 |
| 历史读取或快照返回期间任务结束 | 最终显示终态，不被迟到快照恢复成运行中 |
| 恢复期间持续输出及工具完成 | 恢复前后内容连续，未完成工具能正确更新为完成或失败 |
| 恢复期间快速切换会话或重复点击重连 | 只有对应会话的最新恢复结果生效，无重复订阅归并 |
| 两个 attach 乱序，旧请求最后尝试绑定 | 后端拒绝过期绑定，后续事件持续进入当前订阅，不能仅前端显示恢复成功 |
| attach 前已启动异步差异刷新或准备操作 | 完成、失败和取消事件能抵达新订阅或被恢复过程完整补齐 |
| 后台准备、压缩、停止以及空闲 | 各操作可用性符合实际状态，输入得到保留 |
| 运行中补充要求及停止 | 使用同一任务的引导和停止入口，不额外创建任务 |
| 提交超时但后台已启动 | 不自动重发，核对后显示对应运行任务 |
| 提交超时，任务在核对前完成、失败或取消 | 按 requestId 恢复对应终态，消除未知占位，不提示作为未执行需求重试 |
| 提交仍在途，核对时未发现请求记录 | 保持接收结果未知，不能返回确定未接收并允许重复执行 |
| 未确认提交含文本、图片和文本附件，切页或恢复历史后核对 | 原始内容完整保留；确认后与历史关联，拒绝后可恢复编辑，未知时不清理 |
| 核对期间用户在原会话或其他会话编辑新草稿 | 旧提交结果不覆盖新草稿、不恢复到错误会话 |
| 占用拒绝或状态核对失败 | 不误报网络连接故障，不误显示空闲，不丢失输入 |
| 无进程、完整应用重启、只读及归档会话 | 遵循现有生命周期和权限限制，不恢复旧进程或重放输入 |
