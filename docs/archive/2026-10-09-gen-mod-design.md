## 2. pi 接入与 Orbit 的借鉴边界

参考 Orbit 固定版本 `8ee98d6816854405f8187a53a40e5471505fe2d8` 的源码，而非仅依赖 README：

- [bridge.rs](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/src-tauri/src/bridge.rs)：启动 Node + pi RPC，读取 JSONL，通过 Tauri Channel 回传；会话列表另调用 SDK。
- [rpc.ts](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/src/lib/rpc.ts)：请求 ID、响应匹配、超时、连接及高频事件合并。
- [protocol.ts](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/src/lib/protocol.ts)：将 pi 事件转换为消息和工具状态。
- [bundle-pi.mjs](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/scripts/bundle-pi.mjs)：准备内置 pi 与 Node 运行时。

借鉴通信、生命周期和事件归并。React、Zustand、assistant-ui 页面不直接迁移；远程控制、多工作区并行、电脑操作、多 Agent、终端模拟器不纳入首期。

```text
Vue 页面 → piClient 服务 → Tauri invoke → Rust 进程桥 → pi RPC
Vue 会话状态 ← 事件归并器 ← Tauri Channel ← stdout JSONL
                                                    ↓
                                       模型端点 / 项目文件 / skills
```

Vue 不直接调用模型 API，也不在 WebView 内运行 Node SDK。Rust 负责进程、路径、资源与凭据读取；pi 负责模型会话和工具循环。参考[官方 RPC](https://pi.dev/docs/latest/rpc)与[SDK](https://pi.dev/docs/latest/sdk)。

### 2.1 最小通信接口

初期提供连接、发送命令、断开连接三个原生入口；前端服务包装 `connect`、`prompt`、`abort`、`newSession`、`resumeSession`、`getState`、`getMessages`、`getCommands`。这些服务名是应用接口，不冒充 pi 原生命令；具体映射以锁定版本的[RPC Commands](https://pi.dev/docs/latest/rpc-commands)为准。

每次请求生成唯一 ID，保存 Promise 与超时句柄。收到 response 按 ID 结算；断线时拒绝全部待响应请求。命令超时与任务执行时长分离，不能用 30 秒请求超时判断长时间构建失败，也不能在响应不明确时自动重发生成任务。

stdout 只解析 LF 分隔的完整 JSON 对象，保留未完成记录；stderr 单独作为诊断。协议错误、模型错误、工具错误、进程退出分别展示。前端订阅建立后才启动进程，避免丢失早期事件。

### 2.2 会话、取消与完成

首期只允许一个活动生成任务。运行时允许取消；追加需求先在输入框保留，空闲后发送，暂不实现 steer/follow-up 双队列界面。

连接状态与任务状态独立：连接为未连接、连接中、已连接、异常；任务为就绪、提交中、执行中、取消中、结束或失败。`prompt` 响应成功表示请求被接受、排队或已处理，按 `data.disposition` 分别处理：

- `started`：本次请求启动任务，进入执行中并等待 `agent_settled`，同时处理先于响应到达的任务事件。
- `handled`：本次输入已被扩展或输入处理器消费，直接结束本次提交，不等待一个未启动任务的 `agent_settled`。扩展可能另行启动工作，实际活动状态仍由事件和 `getState` 判断，不强制将已有任务改为空闲。
- `queued`：请求已排队，不能当作已启动或完成；首期不主动发送队列请求，若收到该结果则结合实际事件和状态跟踪，不自动重发。

`agent_settled` 表示自动工作停止。交付是否成功仍取决于消息、工具结果和产物检查，不能收到结束事件就显示“MOD 可用”。上述分支参考[官方 RPC 生命周期](https://pi.dev/docs/latest/rpc)与[命令响应](https://pi.dev/docs/latest/rpc-commands)。

取消先发 abort，等待结束；无响应时提供重启进程入口。任务进程与通用命令启动的子进程需要一起清理。窗口关闭时释放进程和订阅。重启恢复会话历史，但不自动继续可能产生写入的任务。

pi 会话文件是对话历史的权威来源；应用只保存项目与会话路径关联、skills 快照和产物记录，不另存一份可编辑对话。会话切换不能将旧连接迟到事件写入新状态，使用连接代次标记过滤。

### 2.3 运行时分发

开发与发布均锁定 pi 版本；发布包携带适配目标架构的 Node 与 pi 运行资源，使用明确路径启动，不依赖系统全局安装。Windows 工具执行优先适配 PowerShell，不默认要求 Git Bash。Node、pi 与必要依赖的资源遗漏、路径空格及中文路径是后续打包验收重点。

应用保存独立的 pi 配置和会话目录，不覆盖用户已有的全局 pi 设置。具体环境变量和启动参数须以锁定版本确认。Orbit 的 macOS 实现只提供参考，不证明 Windows 发布可用。

### 2.4 Orbit 为什么使用 Bun

根据固定版本的[package.json](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/package.json)与上文打包脚本，Bun 在 Orbit 中有三类明确用途：

1. 包管理与脚本运行：`packageManager: bun@1.4.2` 声明项目期望的 Bun 版本，配合 `bun.lock` 和 frozen-lockfile 安装约束统一工具链。该字段本身不保证所有环境自动强制安装这个版本。
2. 测试工具：项目脚本使用 `bun test`，同时仍有 Vitest；不是所有测试都迁到 Bun。
3. 构建工具：`bundle-pi.mjs` 调用 `bun build --target=node` 打包 pi CLI、SDK 和 worker，输出供 Node 执行的 JavaScript。

Vite 仍负责前端构建，Tauri/Rust 仍负责桌面程序，pi 仍由 Node 启动。Bun 在此承担开发工具角色，不是 pi RPC 的要求，也没有把桌面运行时替换成 Bun。固定版本和集中工具链有助于可重复构建；源码没有提供其性能选择理由，不能断言作者是为了某个实测提速。

本项目暂保留 pnpm 和现有锁文件。若后续直接借鉴 Orbit 的 Bun 打包路径，则需要明确增加并固定 Bun 为构建工具；也可以另外设计 Node 工具链的打包方案。该打包依赖在实现阶段定案，不混用两份依赖锁文件，不因为声明 `packageManager` 就假定 Bun 已安装。桌面发布继续携带 Node/pi，用户无需为了运行产品安装 Bun。

## 3. Skills：通用流程 + 游戏能力

Skill 是指令、资料、模板和脚本的组合，不是自动拥有新权限的插件。pi 先暴露 skill 名称与描述，按需读取完整内容；显式 `/skill:name` 可强制调用。参考[官方 Skills](https://pi.dev/docs/latest/skills)。

### 3.1 首期能力组织

| Skill                | 职责                                              | 交付                                |
| -------------------- | ------------------------------------------------- | ----------------------------------- |
| `mod-workflow`，通用 | 理解需求、组织工程、按统一格式交付文件与安装清单  | 源码、产物清单和交付说明            |
| `duckov-mod`，游戏   | 游戏资料、C# 入口、模板、依赖准备、构建与安装布局 | Duckov MOD 文件和通用格式的安装清单 |

首期不拆出大量单步骤 skills。两个 skill 各自独立，`duckov-mod` 明确要求配合已启用的通用流程；应用在任务上下文中提供两者名称、完整路径和读取要求。pi 不保证自动实现 skill 依赖，依赖选择由应用负责。

```text
skills/
├─ common/mod-workflow/
│  ├─ SKILL.md
│  └─ references/delivery.md
└─ games/duckov/duckov-mod/
   ├─ SKILL.md
   ├─ references/          # 游戏接口资料及来源版本
   ├─ assets/              # C# 工程、info.ini、预览图模板
   └─ scripts/             # 依赖准备、构建、打包
```

目录按职责分类；每个 skill 的 name 全局唯一。`SKILL.md` 使用标准 frontmatter，应用自己的分类、gameId、版本、依赖、启用状态放在单独的 skill 目录清单，不扩展 pi 标准字段来冒充加载能力。

### 3.2 发现、安装与启停

内置 skills 随应用分发，另支持导入本地 skill 文件夹到应用数据目录。首期不做远程 marketplace、自动更新或 npm/git 安装界面。导入检查 SKILL.md 名称、描述、引用路径与重复名称，展示来源和脚本；导入动作不执行脚本。内置 skills 不直接改写，用户副本必须使用不同名称。

管理页区分“已安装”“已启用”“本会话已加载”。展示通用/游戏分类、名称、说明、版本、来源、依赖与加载错误。其他游戏 skills 可以安装，但当前 Duckov 项目只加载所选游戏及所需通用 skills。

使用 `--no-skills` 关闭自动发现，再逐项传入启用 skill 的 `--skill` 路径；只显式加载应用 extension，避免任意项目资源混入。官方 CLI 支持该用法，参见[资源参数](https://pi.dev/docs/latest/cli)。禁用意味着下一会话不加载，不能只隐藏条目。

启停和更新在任务空闲时重建进程生效。已读入历史的 skill 指令无法靠禁用撤回，因此禁用/版本变化后新建会话，保留旧会话只读查看，避免声称恢复旧上下文后仍完全隔离。每个会话记录 skill 名称、版本和内容摘要，便于追溯。

Orbit 的[SkillsPage](https://github.com/ErKeLost/Orbit/blob/8ee98d6816854405f8187a53a40e5471505fe2d8/src/features/settings/SkillsPage.tsx)读取的是命令列表，显示开关只隐藏条目。我们的安装清单是管理入口，`get_commands` 用于对照实际可调用状态，不作为安装清单的唯一来源。

### 3.3 执行边界

Skills 承载游戏知识与开发规则，extension 提供通用文件、命令及产物交付工具。默认交付流程通过通用命令整理文件并打包 ZIP，不设置独立的手动 MOD 构建流程。需要编译的 MOD，由对应 skill 规定依赖、工具链和命令，AI 在生成任务中通过通用命令执行并记录结果；游戏入口和安装目录布局也由 skill 规范。桌面程序不为每个游戏增加独立环境检测、构建或安装分支。新增游戏以新增 skill 和资料/脚本为主，只有现有通用工具确实无法执行时才扩展工具能力。

开发和产物写入稳定的 MOD 工作目录；用户点击安装后，通用安装器才向选定目标复制文件。`cwd`、skill allowlist 和系统提示都不构成文件沙箱。应用工具负责通用路径校验、任务子进程和文件交付，不把游戏规则硬编码进 Rust 或 Vue。安装依据结构化清单执行，不运行模型生成的任意安装 shell 命令。

## 4. 逃离鸭科夫首期闭环

**建议首期范围**：基于游戏现有 API 的 C# 逻辑 MOD，从自然语言需求生成或修改工程，构建 DLL，整理发布目录。优先用简单 UI/信息展示类 MOD 验收。新增武器、角色模型、地图、动画、AssetBundle、Unity 编辑器自动化和创意工坊发布不作为首期完成条件；这是范围建议，需要开发前审查。

[Duckov modding 示例](https://github.com/xvrsl/duckov_modding)介绍了 C# 类库、游戏程序集引用及入口对应关系。文档不能代替用户实际安装版本的 API；资料应记录来源和版本，未查明的成员不得让模型凭空编造。

### 4.1 环境与工程

创建项目只选择游戏对应的 skill、填写 MOD 名称与需求，不强制选择游戏安装目录，也不检查游戏是否已安装。应用提供统一工作区和工具执行能力；依赖、工程模板及构建要求由 skill 说明和处理，不做逐游戏环境检测页面。

未安装游戏仍可生成源码。编译需要的 SDK、参考程序集或开发包由 skill 指定来源，允许用户提供独立参考目录，不要求其来自本机游戏。若确实缺少构建依赖，保留源码并说明缺失项；不能用伪造程序集或空产物冒充已构建。编译依赖与游戏安装是两回事，不将缺依赖解释为必须安装游戏。游戏运行、测试与效果验证由用户自行负责。

Duckov skill 可参考示例采用 `netstandard2.1`，并统一工程名称、DLL 名、info.ini name、namespace 和 ModBehaviour 入口。具体依赖和版本由 skill 资料及用户提供的参考文件确定，不要求桌面程序验证本机游戏版本。需要的路径作为参数传递，不拼接为 shell 字符串。

### 4.2 生成步骤与错误路径

1. 新建 MOD 项目并选择 Duckov skill；无 Key 时保存需求，不发模型请求，不要求安装游戏。
2. AI 读取通用流程、游戏资料和当前源码，明确需求；有业务歧义先追问。
3. 在工作区生成/修改源码，记录涉及文件；沿用已有项目时展示变更说明。
4. AI 按 skill 使用通用命令准备交付文件，通常直接打包 ZIP；Duckov C# MOD 需要先编译 DLL，再打包，编译也是通用命令的一部分。记录命令退出码和日志，不要求用户另点“构建”，不自动运行游戏测试。
5. 命令失败保留源码和诊断，不登记成功版本；用户可触发“让 AI 修复”继续会话，不无限自动重试。
6. 校验本次文件与 ZIP 后，登记独立产物版本，保存到该 MOD 的固定目录并展示在管理面板。
7. 用户选择产物版本并点击“安装”，选择目标目录；应用按该版本的安装清单复制文件并记录结果。也可打开版本目录或导出该版本 ZIP。

Duckov 打包内容为 MOD DLL、info.ini、预览资源和说明；额外依赖按明确的 skill 规则收集，不包含游戏运行库。ZIP 只是交付容器，不能替代 C# MOD 所需的编译。产物登记必须校验文件存在、名称对应、必要命令退出码及 ZIP 内容与本次文件清单一致，不从 AI 的自然语言结论推断成功。旧 DLL 或旧 ZIP 不得当作新产物；每个成功版本记录版本 ID、任务 ID 与时间。

生成完成后不自动安装或启动游戏；通过管理面板的按钮安装。安装只负责将产物放入用户指定位置，是否能被游戏加载及效果是否正确由用户自行验证。发布说明记录 AI 参与生成，和游戏示例给出的 AI 内容标注要求保持一致。

开发状态与安装状态独立：源码已生成、命令执行中/失败、产物已就绪；安装状态按产物版本和目标目录记录。A 版安装成功后生成 B 版，保留 A 的成功记录，B 显示未安装；B 安装失败且回退成功时，目标仍关联 A。界面不显示自动游戏验证结果，也不把安装成功等同于功能验证通过。

### 4.3 通用 MOD 存储与管理

使用应用的本地数据目录下 `mods/` 作为稳定根目录，通过 Tauri 路径 API 获取实际位置，不绑定源码仓库或会话临时目录。每个 MOD 使用稳定 ID，显示名称可修改而目录不变：

```text
<appLocalDataDir>/mods/<modId>/
├─ mod.json             # 游戏标识、名称、skill、开发状态、版本列表与安装记录
├─ source/              # 工程与源码，作为 pi 工作目录
├─ artifacts/
│  └─ <versionId>/      # 每次成功交付使用独立版本目录
│     ├─ version.json   # 版本 ID、任务 ID、时间、skill 快照与文件清单
│     ├─ files/         # 安装文件
│     ├─ install.json   # 该版本的安装清单
│     └─ mod.zip        # 该版本的交付包
└─ logs/                # 通用命令与安装日志
```

生成、继续修改、会话恢复均回到同一 MOD 的 source 目录。每次交付先写独立临时输出，校验成功后保存到新的 `artifacts/<versionId>/` 并登记，已登记版本的文件、ZIP 和清单不再覆盖；修改或重新打包形成新版本。失败不登记成功版本，也不替换既有版本。安装与导出固定使用用户选择的已登记版本，不因出现新版本而切换；关闭应用后仍可找到全部已登记版本。

安装记录保存版本 ID、目标目录、结果与时间；同一目标目录当前关联的版本只在安装成功后更新。失败回退成功时保留原关联，回退不完整时记录异常，不标为旧版仍完整安装。版本 ID 由应用生成并保证同一 MOD 内唯一，不依赖显示名称或模型填写的版本号。

管理面板首期显示名称、游戏/skill、更新时间、开发状态与产物版本列表；选择版本后展示它的安装记录和目标目录，提供“继续修改”“打开目录”“安装”“导出”操作。列表区分最新产物版本与目标已安装版本，例如“B 待安装，目标当前为 A”。无需安装游戏即可开发和管理 MOD；只有安装时需要用户提供目标目录。暂不增加自动发现游戏、多平台扫描或创意工坊管理。

通用 skill 规定安装清单格式：目标目录说明、产物内的源相对路径和目标相对路径；游戏 skill 填充具体布局。应用不根据 gameId 写安装分支，只校验源文件位于所选版本的 `files/`、目标路径位于用户选定目录，然后执行复制并记录安装位置和版本 ID。绝对路径或 `..` 越界清单拒绝执行。

安装时若目标文件已存在，展示覆盖清单并确认，备份本次将替换的文件；失败时回退本次已经写入的文件，保留失败原因与备份位置。源产物始终保留在稳定目录。该面板先完成开发文件管理和按钮安装，不扩展成完整游戏 MOD 启停系统。

### 6.2 结构化消息

页面框架和 Markdown 渲染器各司其职。shadcn-vue + Tailwind CSS 提供可自定义的布局、表单、弹窗、列表与反馈；markstream-vue 只渲染文本部分，不承担会话、工具、产物或模型通信。

参考 Codex 的会话工作台方向组织回复：用户消息保持紧凑；执行期间显示活动状态和可展开的工具过程；最终助手回复突出正文、修改摘要和产物操作。执行过程默认显示工具名称、简短摘要和状态，详细参数/输出展开查看；失败保留可见提示。文件变更在右侧展示路径、摘要与差异，产物以可操作卡片呈现。不能把后台诊断、原始 JSON 或未经提供的推理内容当作默认正文展示；也不能将工具日志归并成模型回复。

消息保留 ID、role、顺序及 typed parts；文本、模型实际提供的推理内容、工具调用、工具结果、错误、文件产物分别存储。工具按 toolCallId 配对，状态为等待、执行、成功、失败或取消。不将所有事件拼成一条 Markdown，也不要求模型用 Markdown 伪造工具结果卡片。

`message_update` 按内容索引累积增量，`message_end` 使用最终完整消息校正。任务结束不代表每张卡片都成功；工具退出码和结果独立判断。产物卡片来自交付工具的结构化结果与文件检查，关联具体版本 ID 和 ZIP，而非模型生成的链接。UI 请求 select/confirm/input 映射为应用弹窗，取消时回传对应响应；首期不支持终端专有扩展界面。

### 6.3 Markdown 与性能

推荐 markstream-vue，项目定位及终态解析说明见[官方仓库](https://github.com/Simon-He95/markstream-vue)。它比只处理完整文档的 markdown-it 更贴近流式回复；Vue 页面无需引入 React 的 assistant-ui。该选择仍需后续在 Windows WebView 中验证。

只开启段落、列表、表格、链接及代码块等首期需要的能力；Mermaid、公式和增强 diff 暂不引入。代码复制与文件定位由应用提供。Markdown 不执行脚本、原始 HTML 或模型指定的任意组件；链接经过应用处理，文件链接校验允许的项目范围。

高频增量按动画帧合并更新，完成/失败事件到来前先冲刷缓冲，不丢弃事件顺序。长工具日志只展示截断摘要，全文保留为日志文件。仅当用户处于底部时跟随滚动，用户向上阅读后停止自动滚动。历史消息保持稳定，只更新活动消息；长会话再按实际需求引入虚拟列表。
