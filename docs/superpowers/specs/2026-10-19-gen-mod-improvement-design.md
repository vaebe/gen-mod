## 1. 本文用途与当前进度

本文将 universal-modder 调研及后续讨论持久化，覆盖七项产品能力与贯穿这些能力的 skills 质量优化。先比较整体收益、成本和依赖，再由用户选择首期范围；选定范围的规格获批后，使用 writing-plans 编写可执行计划，随后按批准范围实现。

本文区分三类信息：

- **已确认需求**：用户已明确选择或项目已有约定，可作为后续设计约束。
- **当前实现事实**：本轮核对的仓库状态，不代表运行验收通过。
- **建议设计**：本文给出的具体方案，需要用户审查后才进入实现。

本文保留设计阶段依据和成本比较。后续用户已选择 P1–P7，并授权限定验证；实现进度与最新检查结果单独记录。第 3 节的现状和后续“待审”表述属于设计时基线，不能作为当前未实现的结论。正常协议中的玩家确认不等于 OS 文件系统隔离：现有子进程拥有当前用户权限，本方案不承诺防御直接篡改 SQLite/JSONL。

重要限制：

1. 当前项目类型没有结构化开发环境、验收记录和跨项目知识实体。
2. Duckov `package.ps1` 当前只收集 MOD DLL、info.ini、preview.png、README.md；不能仅增加说明就声称支持额外素材交付。
3. 正式聊天历史由 pi JSONL 保存；新增记录不能改写历史消息来制造用户确认。
4. 技能版本或任一资源内容变化会改变快照，旧会话按现有机制转为只读；只撤回版本号不能规避内容哈希变化。
5. 当前交付 staging 不支持所有同轮失败重试情形。新增内容检查应尽可能在创建 staging 前失败，不将这一原有限制表述成已解决。
6. 以上均为静态事实核对，未运行应用、测试、构建或游戏。

## 5. 架构方案比较与已选路线

| 方案 | 做法 | 成本与取舍 | 决策 |
| --- | --- | --- | --- |
| A：沿用现有架构 | SQLite 保存结构化事实；目录保存资源；skills 提供游戏方法；原生工具执行确定性操作 | 复用程度高，需要明确新增数据与工具边界 | 用户已选择 |
| B：新增能力以本地文件为主 | JSON/Markdown 保存上下文、验收与经验，界面提供读取和确认 | 文件易检查，但关联查询、并发修改、索引与恢复需要另行维护 | 不采用 |
| C：集成上游 CLI | 将扫描、检查、素材等 Python 命令接入工作台 | 可复用部分代码，但增加运行时、依赖、分发和升级成本 | 不作为总体路线 |

选定路线的职责：

- **Vue 界面**：显示事实与待确认草稿，接收玩家选择，保持普通玩家能理解的语言。
- **Rust 应用层**：校验身份、版本归属、路径与状态，管理持久化和确定性检查，处理用户确认。
- **pi 扩展与工具**：向 AI 暴露范围受控的读写能力，桥接原生请求，沿用任务身份与回执。
- **Skills**：解释适用条件、游戏知识、路线选择和任务方法，不代替原生权限及结果校验。
- **SQLite**：保存可关联、可查询的上下文、反馈、知识元数据和操作状态。
- **项目资源目录**：保存本地素材与必要证据文件；正式聊天仍由 pi JSONL 保存。

不将每个游戏的执行流程固化到 Vue/Rust 中。公共数据协议与工具是通用的，游戏识别规则、素材配方与构建要求由受支持游戏能力声明。

## 6. 建议的玩家流程与界面

### 6.1 创建与补充环境

玩家选择已支持游戏、填写名称并描述需求。已有创建入口保持简洁；游戏版本、参考程序集、前置信息只在影响当前任务时收集，可稍后补充。

AI 读取项目已确认信息与本次环境快照；缺少资料时说明具体缺项和影响，不要求玩家一次填写全部技术字段。未适配游戏提示暂不支持，不自动建立实验项目。

### 6.2 制作与交付

AI 在现有 source 中持续修改，通过真实构建与整理命令交付。新增交付信息包括本次实际功能、验收步骤和内容检查报告；这些与具体版本关联。编译、登记、安装、加载、效果分别展示依据。

### 6.3 玩家反馈与确认

玩家在聊天中描述结果或提供截图、日志。AI 整理草稿，在聊天卡片中显示关联版本、观察结果、验证场景和未验证项；玩家可确认、编辑或拒绝。

保存确认本身不启动新一轮模型调用。卡片提供独立的“继续修复”动作，用户触发后将已确认记录带入原会话或可写的新会话。版本归属不明确时先选择，不能默认归到最新版。

### 6.4 复用现有页面

| 入口 | 建议增加的内容 |
| --- | --- |
| 项目入口 | 查看与补充环境、选择已有参考目录、查看调查结果 |
| 聊天 | 验收草稿卡片、确认与编辑、明确版本后继续修复 |
| 版本详情 | 验收步骤、确认记录、内容检查结果及来源 |
| 版本列表 | 简短验收摘要；原“最新”“已安装”含义保持独立 |
| 现有能力管理 | 查看优化后的 skills 与适用范围，不要求玩家编辑注册 JSON 才能完成日常制作 |
| 项目素材入口 | 导入、预览、检查、选择处理配方与查看交付用途 |

UI 实现前读取项目 shadcn-vue 技能并核对已有组件，按需复用 Card、Dialog、Field、Button、Badge 等，不另造通用控件体系。本文确定功能与信息位置，不宣称具体布局已经完成视觉验收。

## 7. 七项产品能力的建议设计

### 7.1 项目开发上下文

保存游戏版本、参考程序集标识、必要前置、已确认行为约定及资料来源。字段区分用户填写、工具检测与 AI 建议；检测事实保留路径来源、时间和可取得的文件指纹，不把文件版本号直接当作游戏版本。

编辑采用 revision 检查。任务开始时绑定上下文快照；任务期间的环境更改用于后续任务，不悄悄改变已运行任务的依据。旧项目可在信息未知时继续查看和讨论，只有当前任务实际依赖的缺项才阻塞对应步骤。

### 7.2 用户验收闭环

每个新交付版本可带验收条目：前提、操作、预期和证据要求。条目只描述应检查什么，不代表已经通过。

反馈草稿关联 modId、versionId、游戏版本、原消息来源及附件引用。AI 可提出结果为通过、部分通过、失败或尚不能确认；只有玩家确认操作能形成正式记录。记录保留确认时间与当时的内容，后续更正追加关联记录，不用新结论覆盖旧证据。

新版本不自动继承旧版本的通过结果；旧结果作为参考显示。删除版本包后保留历史验收摘要和版本身份，标记产物已删除，不制造可安装文件仍存在的假象。

### 7.3 交付内容检查

在现有任务、命令、revision、哈希与 ZIP 校验之外检查实际候选文件集。

| 分类 | 示例与处置 |
| --- | --- |
| 明确阻止项 | `.env`、明确私钥标记、已知实际凭据、与已选参考目录中受限程序集字节一致的文件；阻止登记并返回相对文件名与处理建议 |
| 需核对项 | 疑似反编译内容、无法确认来源的额外运行库、可能含原版资源的大容器；标记原因，按游戏能力的明确交付规则核对 |
| 完整性项 | 必要文件缺失、清单与 ZIP 不一致；沿用原生既有拒绝逻辑 |

报告不包含命中的密钥正文；只检查交付候选文件和用户已选的必要参考范围，不全盘扫描游戏或用户目录。第三方运行库不能仅凭 DLL 扩展名一律禁止，需区分游戏参考文件与获准分发的前置。

扩展层做创建 staging 前的预检查；原生登记前对最终文件重查决定性约束。AI 无法用自报 PASS 绕过原生检查。无法确认的项不被包装成已完成的许可或合规判断；游戏能力未声明可交付额外文件时，先明确适配缺项。

### 7.4 可复用游戏知识

区分受维护的游戏参考资料与本地项目经验。前者继续保留在 skills 资料中，后者记录适用游戏版本、实现路线、来源及用户验证范围。

本地经验先为候选，由用户选择保存和复用；玩家确认“效果符合预期”不能自动证明某个通用 API 结论。技术说明需链接对应资料或实现依据，检索结果始终显示证据类型。

使用游戏、版本、路线与任务关键词进行本地筛选，优先精确匹配，再展示注明差异的相近资料。初期采用现有 SQLite 与简单字段检索，不预先引入向量数据库或嵌入服务。

不把全部聊天、调试日志或可直接从当前源码读取的事实重复积累成长期知识。只保存有复用价值、未被已有来源覆盖的最小经验，不上传云端，不自动贡献上游 PR。

### 7.5 引擎公共能力

继续沿用 registry 的 `common` 与 `game` 分类，不为引擎新增一套独立执行系统。只有多个实际任务或受支持游戏存在相同需求时，才抽取共用资料或脚本；只有 Duckov 使用的知识仍留在 Duckov。

可复用候选包括参考程序集查证方法、Unity 对象生命周期、资源处理与交付原则。每项抽取必须保留版本条件与游戏覆盖差异，不能让“Unity 游戏”隐含等于“可直接使用某个加载器”。

本轮设计说明抽取条件与扩展契约，不为了展示通用性新增未经适配的游戏或空技能包。

### 7.6 已支持游戏调查

玩家选择安装目录或独立参考目录后，由只读工具按该游戏能力声明的特征检查。记录命中的文件、识别依据、可取得的版本、已存在前置及未知项。

扫描设置明确的文件数量、层级和读取量上限；截断与权限错误显式报告。规则分值只用于候选排序，不显示成概率意义的准确率。无法可靠判断时保留未知，不用引擎识别代替具体游戏适配。

调查结果可由玩家采纳为项目上下文。无安装目录时继续支持独立参考程序集流程；不自动改注册表、安装加载器、启动游戏或查找整台电脑。

### 7.7 本地素材导入与处理

导入是将玩家主动选择的文件复制到项目素材区，记录原文件名、大小、类型与哈希；不将素材继续绑定在可能被移动的外部绝对路径上。

基础处理建议先覆盖 PNG/JPEG 图片的尺寸检查、缩放、裁剪和 PNG 透明度保留。原图保留，处理结果生成新文件，并保存配方与输入指纹。预览只证明文件可展示，不证明游戏能够加载。

音频、模型、AssetBundle 和游戏专属格式按成本比较独立列项。没有已实现处理器或对应游戏规范时提示不支持转换，不能把格式改名当转换；不默认引入 ffmpeg、Blender 或新的第三方运行时。

只有声明了实际交付方式的素材才能进入版本包。Duckov 需同步扩展资源清单与打包脚本，并核对 MOD 如何从安装目录加载资源；当前已知的四文件打包方式不能被描述为已经支持任意素材。

## 8. Skills 质量优化专项

### 8.1 规范与评价依据

格式依据 [Agent Skills specification](https://agentskills.io/specification)，编写依据 [Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)，结合本机 skill-creator 和 writing-skills 的适用要求。

区分标准要求、最佳实践与当前宿主约束：name/description 等按格式标准与应用解析器一致维护；正文按任务渐进披露；不机械要求所有描述使用英文、固定章节数量或统一字数。技能要适应 GenMod 的 pi 工具和权限，不能照搬其他宿主专用字段后假定已经生效。

### 8.2 当前可改进项

- Duckov 入口混合任务导航、调查、完整构建参数和交付要求，可拆清稳定入口与条件性细节。
- 通用技能、游戏入口及专题资料存在重复约束，需要为每项内容明确权威位置。
- 限制与提醒较多，需要补充能改变决策的正向方法及小而可信的示例。
- 游戏 API 的来源和验证状态需要在使用位置清楚呈现，避免把定位线索当作当前契约。
- 现有静态检查只能说明元数据与引用有效，不能证明模型实际会正确选择资料和调用工具。

这些是内容与结构的优化依据，不等同于已复现的模型行为缺陷。

### 8.3 职责与目标结构

| 层次 | 建议职责 |
| --- | --- |
| `mod-workflow/SKILL.md` | 持续开发、通用任务边界、工具选择与交付入口 |

每条指导应回答适用条件、必要输入、建议处理及结果确认。通用常识、重复的禁止语句和宿主已保证的机械约束不多处展开；仍保留会影响正确性的游戏特有条件与工具不可绕过的契约。

不将专题全部拆成独立 skill：当前任务导航已能按需读取，只有出现真实独立触发需求时再拆分。描述同步到 registry，依赖仍通过当前解析器解析。

### 8.4 资料与示例

优先整理仓库已有且有直接来源的例子，例如 MOD 入口、物品悬浮 UI、参考程序集查证和缺依赖处理。每例注明适用条件、已核对来源、需要重新核对的签名和未验证部分。

没有当前参考程序集或对应版本实现时，不新增看似可运行但没有依据的游戏成员。复杂功能只有调查路线时就明确提供调查方法，不用空壳模板伪装成完整能力。

脚本优化只覆盖实际计划选定的构建、交付与素材路径；保持必需原始脚本成功记录和 fresh output 约束，不能仅为缩短技能正文而绕过原生校验。

### 8.5 质量验收

静态层检查格式、描述与 registry 一致性、相对引用、重复与冲突、宿主可用工具、来源与版本说明。

行为评估覆盖新建简单 MOD、已有源码续改、缺参考程序集、API 版本不符、构建失败、额外资源交付及玩家反馈整理。观察实际读取和工具行为，而不是只检查最终回复或标题是否包含某个词。

正式执行计划须写明所用模型、环境、允许工具、隔离目录、成功标准和运行成本。当前没有运行这些评估；子代理、测试或模型调用不因本设计自动获得授权。没有游戏内证据的评估不得声称证明 MOD 效果。

### 8.6 已有六文件改动如何处理

现有未提交改动作为候选材料：有价值的调查、反馈与证据要求保留；重复或职责放错的内容合并、移动或重写。最终结构按本设计审查结果确定，不为维护先前输出而强行保留。

本次不还原这些文件，也不把它们计为本方案全部完成。实现时重新核对差异，只修改获批部分；整体变更最终确定后统一确认技能版本与资源哈希，避免每个草稿都无意义递增版本。

## 9. 建议数据模型与存储边界

以下是概念实体与关键字段，不是已经实现的数据库迁移：

| 实体 | 关键字段 | 边界 |
| --- | --- | --- |
| ProjectContext | modId、revision、gameVersion、referenceSets、prerequisites、confirmedRequirements、sources | 玩家环境与已确认约定；未知字段可缺省 |
| ContextSnapshot | snapshotId、modId、taskId、contextRevision、payload、createdAt | 任务开始时固定，不被后续编辑改写 |
| DeliveryMetadata | modId、versionId、taskId、contextSnapshotId、cases、checkReport、artifactDeleted | 关联不可变版本；独立于包内 version.json 保存 |
| FeedbackDraft | draftId、modId、versionId、revision、observations、proposedResult、sourceMessages、evidenceRefs | AI 只创建草稿，不能写玩家确认字段 |
| VerificationRecord | recordId、modId、versionId、gameVersion、caseResults、confirmedAt、sourceDraftId、supersedes | 玩家确认形成，保留历史更正关系 |
| KnowledgeNote | noteId、gameId、applicableVersion、route、content、sourceRefs、evidenceKind、status | 候选、可用、归档；技术依据与效果反馈分开标注 |
| ProjectAsset | assetId、modId、relativePath、sha256、mediaType、originalName、recipe、inputAssetId | 原素材和处理结果分开记录 |
| InspectionReport | reportId、modId、gameId、selectedRoot、findings、unknowns、limits、inspectedAt | 只读检测结果，不自动变成已确认上下文 |

关联规则：

1. 所有记录由原生验证所属项目，versionId 必须指向该项目真实登记过的版本。
2. 当前版本保存在项目 payload 中；新增关联数据需有独立版本元数据锚点，删除包后保留锚点与历史记录，不对不存在的关系声明数据库外键保证。
3. 确认草稿使用 expectedRevision，避免玩家查看后内容又被 AI 更新却仍确认旧画面。
4. 截图和日志优先引用原聊天证据；必要导入文件保存到项目证据区，并保留内容指纹。消息不可用时明确标记，不编造证据。
5. 反馈、上下文、知识和原素材不写入 source，避免单纯记录反馈触发源码 revision 变化。进入构建的素材副本才按源码写操作处理。
6. SQLite 使用现有短事务；文件复制与元数据之间沿用可恢复操作记录模式，不持有数据库事务等待模型或大文件处理。

建议项目目录扩展为 `evidence/` 与 `assets/originals/`、`assets/derived/`。source、artifacts、logs 继续保持原职责；项目数据不写到仓库 docs 或长期助手记忆中。

建议新增的工具能力如下，最终接口在获批子项目的执行计划中固定：

| 能力 | AI 可以做 | 原生必须保证 |
| --- | --- | --- |
| 读取上下文 | 读取当前任务快照与来源 | 绑定项目和任务，不接受任意数据目录 |
| 建议上下文变更 | 提交需要玩家核对的字段草稿 | 不静默覆盖玩家确认的约定；检测事实与建议有来源区分 |
| 提交验收草稿 | 引用原消息、版本和附件，整理观察结果 | 校验真实归属与消息来源；拒绝模型自填 confirmedAt |
| 检索经验 | 按游戏、版本、任务查相关条目 | 返回来源和验证范围，不把笔记正文当系统指令 |
| 提交经验候选 | 提出值得复用的最小知识 | 不自动批准跨项目复用或上传 |
| 读取调查结果 | 查看玩家已选择范围的只读结果 | 不扩大读取目录，不自动安装或修改游戏 |
| 处理素材 | 使用已有 assetId 与批准的配方生成新结果 | 原图不覆盖；资源进入 source 时接入已有租约与 revision |

玩家确认、拒绝和编辑通过应用 UI 的 IPC 完成，不作为 AI 可调用工具。继续修复是独立用户动作；正式聊天历史仍保留原始输入，不以整理后的记录替换。

上下文与经验按当前任务相关性选择，避免每轮注入完整知识库和全部历史反馈。新工具使用原有任务身份与进程桥接，不引入第二套运行时。

## 11. 错误、并发与兼容处理

- **缺资料**：保留已有源码与记录，明确阻塞项；不相关的已授权工作继续。
- **没有模型或图片能力**：允许查看环境、素材和历史记录；需要 AI 的动作说明缺项，图片不能被静默忽略。
- **反馈版本不明**：先选择对应版本，保留原输入，不按“最新”猜测。
- **草稿同时修改**：expectedRevision 不符时要求重新查看，已确认记录保持不变。
- **文件导入失败**：不登记不存在的素材；已复制但未登记的文件通过恢复记录核对，不误报成功。
- **内容检查失败**：返回具体相对路径与规则，不返回密钥；保持源码和原素材，不能登记为成功交付。
- **扫描不完整**：返回截断、权限或格式原因，未知项保持未知。
- **资源处理不支持**：保留原文件并解释缺少的处理器，不运行未经授权的安装命令。
- **应用重启**：新增记录可恢复；沿用旧任务中断规则，不自动重发需求、继续修复或调用模型。
- **旧数据**：新增字段有明确缺省，旧版本显示“无结构化验收记录”，不反向推导为通过或失败。
- **技能更新**：保留既有快照语义，旧会话只读；新会话加载更新能力。优化 skills 不顺手迁移这项机制。
- **版本删除**：保留验收与环境摘要；已部署文件及安装历史按现有规则处理，不随新增元数据删除。

## 14. 验收设计与执行授权

### 14.1 方案级验收标准

- 未支持游戏不会进入制作流程；已有项目和历史版本仍可读取。
- 当前任务使用固定上下文快照，新环境编辑不会改写旧任务依据。

- Skills 按任务读取必要资料，不要求不存在的工具，不编造缺失 API 或成功回执。
- 重启、旧数据、版本删除和重复操作不会制造重复确认或丢失正式记录。
