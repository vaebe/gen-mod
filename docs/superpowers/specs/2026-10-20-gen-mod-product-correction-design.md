## 4. “全部文件”增加导入和移动

### 4.1 玩家流程与范围

1. 打开现有“全部文件”，选中目录后点击“导入文件”。未选目录时默认项目 `source` 根目录；选中文件时默认其父目录。
2. 通过原生文件选择器选择一个或多个普通文件，选择后直接原样复制进目标目录，不再要求无冲突情况下的导入确认；目标文件内容与原件一致，外部原文件保持原样。不经过素材处理管线，不自动解析、转换、压缩、裁剪或生成衍生文件。
3. 文件立即进入同一棵文件树，沿用当前文本和图片预览。其他类型显示大小与不可预览原因，仍然可以导入和移动。
4. 选中项目内文件，点击“移动”，从项目目录中选择目标位置；支持同目录改名，不自动修改源码中的引用。
5. 移动后选中新位置，刷新源目录、目标目录和预览；聊天下次任务可得知实际文件变化。

按已确认范围，支持多文件导入、单个文件移动与改名，以及在目标选择器中创建单层目录。导入不按文件类型筛选；已有预览按玩家选择文件查看时触发，预览限制不作为导入限制。首期不包含目录整批导入、目录移动、批量改名、拖拽整理、删除或跨项目移动。

目标选择器只浏览当前项目 `source` 内的目录。项目内部文件名和界面展示采用相对路径；不会把“选择目标目录”变成任意磁盘写入。

### 4.2 冲突与失败规则

- 同名冲突不覆盖，也不自动追加随机后缀；复制前发现冲突时标出，允许改目标文件名或跳过该项，其他无冲突文件直接复制。Windows 大小写等价名称按冲突处理；仅修改大小写的改名本期明确提示暂不支持。
- 多文件先检查全部目标与重复名称。提交时逐文件原子落盘，逐项报告成功和失败；中途失败不假装整批成功，也不删除已经成功导入的文件。
- 导入使用流式文件复制，不增加素材类型、尺寸、像素、解码或业务内容检查，不另设本方案此前拟议的文件数量和大小上限。路径有效性、重名冲突、实际读写错误及项目写协调属于必要文件操作检查；不把二进制整份装入前端或编码为聊天文本。
- 拒绝符号链接、重解析点、特殊文件、越界路径及保留内部目录。`.delivery`、`.git` 和当前技能声明的构建排除目录不能作为导入或移动目标。
- 提交前再次核对来源与目标状态。来源读取失败、复制期间变化、空间不足或目标被占用时报告该项失败，不留下被误认为成功导入的半文件。
- 移动限定同一项目文件树；目标已经存在时拒绝。移动会影响引用，界面提示后由玩家确认；AI 可在后续任务按需求修正引用，不在移动动作里偷偷重构代码。
- 导入完成后只刷新文件树与变更状态，不自动启动 AI、构建、打包、扫描内容或修改文件引用。后续任务中的读取、使用和交付检查是独立动作，不属于导入步骤。

### 4.3 与 AI 并发、源码变更和交付的关系

原生文件操作在现有 `Workspaces` 上增加来自 UI 的操作身份，使用与 AI 共用的项目级写协调；不伪造 taskId、模型工具回执或编译记录。预复制可在项目受控临时区完成，最终提交、路径复核和 revision 更新必须受共享写协调保护。

导入临时路径在复制前写入操作记录，位于项目根的 `.source-imports/<operationId>/`，不放进 source；复制完成、同步并登记结果哈希后才以不覆盖移动提交。异常退出不依赖临时文件析构，重启只处理已登记、确认归属的路径；不扫描清理任意 `.tmp`，也不自动从外部原路径重新导入。

玩家发起文件操作时，原生端检查该项目是否有活动 AI 任务：有则拒绝提交，保留选择并提示任务结束后重试；不自动排队到用户离开界面后执行。任务启动与 UI 文件提交必须使用同一协调入口，避免“检查空闲后恰好启动任务”的竞争。不同项目之间不相互阻塞。

成功导入或移动要更新源码指纹、revision 和文件变更通知，并记录真实的 UI 操作来源。当前没有活动任务时，不伪造本轮 AI 差异；下一任务以变更后的源码建立基线。若界面正在展示历史任务差异，其历史基线保持不变。

旧构建回执不能为变更后的源码登记新版本；实际交付文件必须重新构建并经过现有检查。既有版本包不随源码移动而改变。

### 4.4 素材处理与打包

用户已明确图片按普通文件直接导入，并在后续集中审阅中明确认可移除独立素材库、配方表单、assetId 选择、二次“加入源码”步骤，以及专门裁剪缩放和相关模型工具。删除范围的依据是这次后续确认，不是从“导入不处理”自行推导。

已有 Duckov `ResourceManifest` 与打包校验继续保留，因为它解决的是实际资源交付问题。是否加载、如何加载某个文件，由对应游戏 Skill 与本次 MOD 实现决定；文件被导入并不意味着它会自动入包或在游戏中生效。

## 5. 只读 Skills 与可编辑的跨项目长期记忆

### 5.1 本次选定的边界

已有通用 `mod-workflow` 负责预置公共制作流程，`duckov-mod` 负责预置 Duckov 差异，详细资料继续位于各自 `references/`、模板与脚本。没有第二个已验证游戏共性需求时，不新增空的 Unity 公共 Skill。

开发中新积累的可复用知识保存到应用自己的长期记忆数据中，供同一用户的其他相关项目检索。保留并改造现有 `knowledge/` 与检索能力，将原 `propose_knowledge` 的候选接入改为真实自动保存并返回持久化回执；来源、版本过滤和并发控制继续利用已有机制，不新建另一套重复知识库。不保留必须人工采纳后才能使用的新记忆流程。

**运行时 AI 无权直接修改 Skills，这是已确认约束，不是一个可以开启的自动学习选项。** 其职责是读取、选择并执行现有方法；不提供创建、编辑、覆盖或更新 Skills 的模型工具。这里的 Skills 包括 SKILL.md、references、模板、脚本及注册声明。

玩家在某个项目中说“成功了”，先形成该版本的验收事实。AI 可以据此保存值得复用的长期记忆，但必须保留“玩家观察”的来源与实际适用范围，不能改写成已验证的通用 API 事实。应用内不存在将该记忆提升、同步或写回 Skills 的流程。

长期记忆与项目记忆分工明确：可复用方法进入长期记忆；“本项目只改文字”“本项目选了哪个参考目录”属于项目记忆。某份源码已有的信息仍读取源码；整段聊天、构建日志和未经确认的猜测不直接积累为长期知识。本方案中的记忆都属于产品数据，不写入本次开发助手的机器级记忆目录。

### 5.2 Skills 本轮具体调整

以下为本仓库开发阶段的修改建议，获批后由开发工作执行；不是赋予产品运行时 AI 修改 Skills 的权限。

- 通用 Skill 增加“开始任务先使用本项目记忆，再查当前源码和有关资料”的路由，避免将任务快照当作当前磁盘状态。
- 增加“玩家导入的资源已经是项目文件”的说明：按项目相对路径读取和使用，不要求 assetId，不重复导入到另一素材区。
- 保留已有新建、续改、缺项、构建、交付和反馈分流；公共协议继续只在一个 references 文档维护，不把工具参数堆进正文。
- 游戏 Skill 继续承担真实 API、程序集、构建脚本与资源加载的差异。未经证据核对的经验不写成可用 API，不把单次玩家验收升级为通用保证。
- 增加长期记忆的检索、来源核对、自动保存和成功后提示的使用路由，明确禁止通过修改 Skills 保存经验。
- 更新当前资料中已撤下素材工具的说明与示例，并同步运行时允许工具列表；不顺手重写无关专题。

系统提示词只保留“何时读取记忆与 Skills、不能把资料当授权”等基础规则，不嵌入长篇游戏教程。

### 5.3 积累、保存和手动更改

采用已确认的“AI 自动保存，用户事后可管理”方式：任务或玩家验收产生有复用价值的结论时，AI 通过原生工具实际保存长期记忆，成功后在聊天中提示已保存的内容及查看、修改、删除入口。说明适用游戏及版本、来源；保存后即可按适用范围参与后续任务检索，无需玩家先采纳。不要求每次交付都保存记忆，也不因用户确认某个 MOD 可用就自动形成全局规则。

只有得到持久化成功回执才能提示“已记住”；保存失败说明失败，不展示成功提示。重复来源与内容不重复创建条目。自动保存不能静默覆盖用户手动修改的内容，也不能自动恢复用户已经删除或停用的记忆。

知识身份不随任务或证据来源改变：稳定键以游戏、主题和适用版本范围生成，不包含命令回执、用户消息等单次来源 ID。新建前还按规范化正文指纹查找用户维护及撤回身份，防止换来源、换主题或省略条目 ID 后重新保存相同旧内容。指纹只保留哈希关联，不保留被删除正文；不声称可以自动识别任意语义改写，Skills 明确禁止以改写内容规避用户决定。

按已确认决定，在应用设置中提供统一的“长期记忆”页，跨项目查看已保存条目；聊天保存提示直接打开对应条目，不另建聊天侧栏管理面板。主界面显示标题、内容、适用范围和状态，支持手动新增、编辑、停用与删除；常规编辑只要求自然语言内容，当前游戏和来源尽量自动关联，不要求用户填写实现路线、证据枚举或技术 ID。

用户手动保存即为明确操作，不再经过 AI 采纳；手动添加或修改的内容标记为用户维护，保留原有来源以供核查，但不能继续冒充与旧证据完全一致的验证结论。技术真实性仍以当前文件、参考资料及实际回执核对。用户可以改记忆，但记忆内容不能赋予 AI 修改 Skills、绕过工具或访问其他项目私人内容的权限。

编辑保存使用条目 revision；其他界面先修改后，不静默覆盖，保留输入并提示重新核对。用户停用或删除后不再用于新任务检索；自动保存需核对原条目的用户维护及删除状态，避免将旧内容重新写回。原有待确认候选作为兼容记录处理，不转为新的人工确认必经步骤。

自动保存并提示、用户可查看修改删除、AI 不能修改 Skills、设置中的统一长期记忆页及聊天直达入口均已由用户明确。具体组件布局在执行计划中按现有设置页和 shadcn-vue 组件安排。

### 5.4 检索、适用范围和任务一致性

长期记忆按当前游戏、已知版本和本次任务关键词检索，沿用有界、可解释的筛选；默认最多 5 条、每条最多 2000 字符。跨项目不等于跨游戏：游戏特定记忆不应用于其他游戏；只有用户明确设置为通用的方法才可跨游戏使用。版本未知时不把某一精确版本的结论当成当前事实。

任务输入将长期记忆标记为参考数据，附条目 ID、revision、适用范围与来源，不写入 systemPrompt 充当基础规则。用户可编辑和版本匹配也不代表内容永远正确，AI 仍需核对当前任务依据。

本任务实际读取的记忆保留当时的内容及版本依据；用户在其他界面修改、停用或删除后影响后续任务，不改写已经运行任务的依据。历史快照仅用于追溯，不允许将已停用内容重新混入新任务。不存在云端共享、向量服务、自动修改 Skills 或后台无条件积累整个聊天的能力。

## 6. 项目环境改为 AI 项目记忆

### 6.1 保存内容与来源

“项目记忆”是本产品的项目上下文能力，不涉及助手在用户机器上的长期记忆目录。本轮沿用 `ProjectContext`、revision 与不可变快照，原建议接入改为有来源的自动更新，不另建通用记忆平台或向量库。

| 信息 | 保存方式 | 可信边界 |
| --- | --- | --- |
| 已确认需求和约束 | 依据当前项目中用户明确表达自动记录，沿用 confirmedRequirements，保存后提示 | 必须关联真实用户消息，不把 AI 推测记成已确认需求；有歧义先询问 |
| 游戏版本、必要前置 | 依据用户明确提供的内容或真实工具结果自动记录并提示 | 发现某个 DLL 或目录标记不等于知道游戏版本和 API 完整性；冲突未解时不默认为最新值 |
| 已选择参考目录及文件指纹 | 玩家在聊天中的“选择参考资料”动作选目录；原生按游戏规则检查并写入 | 不要求玩家输入“目录 \| 文件”技术格式；保留来源报告与构建前复核 |
| 任务、交付、玩家验收进度 | 读取现有任务、版本、验收记录的身份和状态，提供关联摘要 | 不另存一份会与事实记录分叉的完成清单；编译成功与游戏验收分开 |
| 当前源码和素材内容 | 需要时读取实际项目文件 | 不复制为永久记忆，不以旧摘要替代当前文件 |

自然语言需求和前置继续复用当前字段，但需要补齐消息来源关联。字段兼容扩展采用可缺省信息，旧项目不因缺少新来源而无法打开；旧数据明确标记为历史记录，而非追认成新检测事实。

### 6.2 项目生命周期与展示入口

项目创建成功时，在同一项目创建流程中初始化该项目的记忆状态，不等首次模型任务才临时创建。记忆以 modId 隔离，项目内所有会话共享；切换项目后不得显示或更新上一个项目的内容。创建失败时不能留下独立记忆。

现有“项目上下文”面板增加“记忆”Tab，与当前文件、变更和交付等上下文内容并列。展示当前项目记忆及必要来源、资料状态；不另设“项目环境”技术表单，也不将项目记忆混入设置页的跨项目长期记忆列表。没有选择项目时不加载任何项目记忆。

页面及侧边栏的“移除项目”必须区分两种操作：归档只从活动列表和侧边栏隐藏，保留项目记忆、文件、会话及版本，提供归档列表恢复；永久删除才清理当前项目的全部私有数据，包括记忆状态、变更建议、任务快照、源码、交付包和日志，不在新项目中重新出现。原生空闲检查和恢复机制由执行计划落实，不能把当前只有删除会话的代码误当成已有项目删除流程。

归档项目恢复时沿用原 modId 和记忆，不重建项目。永久删除期间阻止迟到的工具回执或界面请求重新写入；文件清理失败明确报告未完成，不宣称全部数据已删除。该操作不卸载游戏目录中的已安装 MOD，不删除独立长期记忆。

非任务连接与空闲进程重启必须从状态核对到进程注册完成持续参与项目预留，防止归档/删除关闭进程后又出现新连接。删除恢复的 pending 和 requires_review 都阻止普通写入及连接，只有恢复并核对身份一致才解除阻断。归档历史读取没有落库或建目录副作用；改名、草稿等真正写入另行检查可写状态。

跨项目长期记忆具有独立生命周期，不依赖来源项目继续存在；来源项目移除后，只保留长期记忆自身的知识、必要来源摘要和适用范围，显示来源项目已移除，不保留或重新暴露项目私人上下文。现有 knowledge_notes 的项目归属外键需要在执行计划中调整，不能因复用旧表而把长期记忆也随项目删除。

### 6.3 项目记忆自动更新

移除“项目环境”技术表单，项目记忆在“记忆”Tab 展示。采用已确认的自动记录方式：用户明确表达的需求、修正和实际工具结果直接保存，聊天中提示本次更新；有歧义才询问，不反复确认用户已经说清楚的内容。不再为每次更新生成必须点击采纳的卡片。

保存必须关联当前项目和真实来源、使用 revision 防止覆盖，不把 AI 推测记成确定事实；只有持久化成功才能声称已记住。相同内容不重复写入或刷提示，失败明确报告。来源冲突且无法判断用户意图时，保留现状并集中询问，不静默选取一个结论。

玩家可在聊天中查看与更正，自动记录明确的纠正并更新“记忆”Tab。缺少资料时按需提供选择参考资料或检查目录动作，不要求完整技术表单。

### 6.4 任务使用与一致性

任务开始时由原生端冻结当前已确认上下文，向 AI 自动提供带类型标记的项目摘要、快照身份和相关历史记录入口；不要只展示一串快照 ID，也不要仅依靠 AI 自己想到调用读取工具。完整内容仍可通过现有读取工具获取。

模型收到 prompt 之前，扩展初始化必须已读取、校验并缓存项目参考消息，向原生回传匹配任务身份与文件哈希的加载成功握手；原生等待失败则终止准备任务。不能依赖 before_agent_start 抛错阻止启动，因为锁定 SDK 会捕获该异常继续运行；该 hook 只返回已经准备好的缓存消息。无需玩家为内部加载再次确认。

摘要按确定规则生成，最多 6000 字符；优先游戏及版本、当前确认约束、资料状态，再是任务和版本索引。超限明确标记未展开内容及读取方式，不能把截断摘要描述为完整记忆。不在 systemPrompt 中把项目自由文本提升为系统规则。

任务期间保存的记忆用于下一任务，不改写本任务快照。其他会话先保存导致 revision 变化时，保留待保存内容，基于最新状态重新核对，不静默覆盖。会话切换和迟到响应继续使用既有 generation 防护。

快照用于记录任务启动依据，不凌驾于当前用户指令：同一任务收到用户明确的新引导时，按新要求继续处理并记录更新来源，不能以快照冻结为由忽略纠正；历史快照保持原样。

文件路径或参考文件可能变化：任务和构建使用前核对当前状态，缺失或指纹变化时提示重新选择或检查；记忆中的旧路径不构成继续访问其他目录的授权。读取记忆失败应明确报错，不伪装为空白新项目。

## 8. 旧数据与兼容

1. **项目和版本**：升级和日常使用不重建项目，不改变已登记版本 ID、包内容、安装记录、玩家验收和旧任务快照；归档全部保留并可恢复，用户明确永久删除时项目记忆与全部项目私有数据一起清理。
2. **项目上下文**：沿用旧 ProjectContext，旧项目补齐记忆初始化状态，保留需求和来源现状，不补造来源。旧待确认建议保留原状态，不因迁移自动应用；只有当前新输入与真实来源能独立支持的内容，才按新流程自动记录。
3. **旧素材**：原图、派生图和旧表保留。已在 source 的副本继续按普通文件使用；素材区中尚未进入 source 的文件不自动搬入，以免意外改变构建输入。发现这类数据时，“全部文件”显示一次性恢复提示，玩家选择后通过同一文件导入流程复制到 `source/assets/legacy/<assetId>.<原类型扩展名>`。核对旧指纹，不覆盖同名文件；原素材不删除。
4. **旧经验**：沿用 knowledge_notes 作为长期记忆的迁移基础。已采纳且允许复用的条目保留原适用游戏、版本、来源和复用状态，满足筛选时可供后续项目检索；candidate、archived 以及 allowReuse=false 不自动升级为跨项目有效记忆。旧版无法区分用户是否修改过正文，因此所有旧条目保守标为用户维护，同事务建立正文指纹关联；不因新证据出现就交给 AI 覆盖。统一入口可查看其原状态，用户明确更改后才改变用途。旧来源保留，不自动转成 Skills，不伪造手动编辑前后的证据一致性。
5. **文件操作中断**：旧导入/处理 pending 继续按已有记录核对和恢复；关闭旧工具后不能遗留会阻塞启动的未知操作。新的导入先登记 source 外临时路径，再复制并登记哈希，最后不覆盖提交；仅清理本次创建、记录明确且确认归属的目标，不能确认时保留并报告。
6. **Skills 更新**：遵循现有内容快照与旧会话只读规则；提示创建新会话继续，不改写旧会话的能力身份。新任务只暴露新工具列表。
7. **迁移方式**：不修改已经使用过的 003–008 SQL。确有新持久字段时追加下一顺序迁移；只扩展兼容 payload 时使用缺省读取。实施计划须依据最终字段选择其中必要部分，不为本方案预建空表。

## 9. 预期体验示例

### 9.1 导入并使用图片

玩家在“全部文件”把 `logo.png` 导入 `assets/`，再说“把这张图用作 MOD 的预览图”。AI 读取实际文件和游戏 Skill，修改工程或打包清单并构建。界面不要求建立素材记录、选择配方或填写资源用途；如果游戏加载图片的方法没有资料依据，AI 明确说明缺项。

### 9.2 另一个项目复用方法

玩家新建第二个 Duckov 项目。AI 使用只读的通用 Skill 和 Duckov Skill，并检索同游戏、匹配版本且已保存的长期记忆，复用此前积累的方法与限制；不会读取第一个项目的私人需求或未经整理的聊天。玩家在“长期记忆”里纠正某条经验后，后续任务读取更正后的内容；游戏特定做法仍核对版本与实际参考资料。

### 9.3 换会话继续制作

玩家已明确“只调整显示文字，不改变颜色”。新的会话开始任务时自动得到该项目约束和已有版本入口，读取当前源码继续修改。玩家说“现在允许改颜色”，AI 自动记录更正并提示，后续任务使用新要求；如果当前任务正接收这条引导，则按新要求继续处理，旧快照和验收记录不变。

## 10. 分阶段实施与验收标准

本节仅确定顺序和验收目标，**不是可直接开始执行的逐任务实现计划**。本方案确认后，再用 writing-plans 编写文件级任务、接口合同、验证命令及检查点。

| 阶段 | 工作 | 验收标准 |
| --- | --- | --- |
| C1 文件入口 | 通用导入、移动、必要目录创建、UI 写协调与通知 | 外部原件不变；冲突无覆盖；成功项可预览；移动在项目内；活动任务期间不产生延迟写入；revision 与交付校验同步 |
| C2 项目记忆 | 项目创建、归档/恢复和永久删除联动、项目上下文“记忆”Tab、按需资料选择、有来源的自动保存及提示、任务摘要 | 项目内跨会话共享、项目间隔离；归档不丢失、恢复沿用、永久删除清理；明确内容无需再次确认，有歧义才询问；切换无旧数据串入；历史依据不变 |
| C3 长期记忆与只读 Skills | 改造知识自动保存、回执提示和检索；提供用户编辑入口；调整 Skills 使用路由 | 无需保存前确认；失败不提示成功；新项目可使用适用记忆；用户改动影响后续任务；停用/删除不被恢复；任务依据可追溯；AI 不修改 Skills、不串读私人需求 |
| C4 收敛 | 移除环境与素材旧入口，迁移经验入口，清除多余业务；已有兼容实现保留 | 新产品入口和工具职责一致，实际分发撤下退役资源；旧库升级、历史数据及旧素材恢复不作为验收条件 |
| C5 文档与验证 | 同步设计索引、现状文档、旧合同状态及资源 | 原设计与新职责可追溯；代码与工具声明一致；报告准确区分静态、测试、应用与游戏效果 |

各阶段实现时同步断开被替代入口，避免用户在过渡版本里同时面对两种管理流程；C4 负责最终清除剩余接入并核对分发。

验收应覆盖：多文件部分失败、重名和大小写冲突、非法路径与链接、任务启动竞争、移动后引用提示、迟到响应、记忆来源与过期 revision、长期记忆跨项目筛选、用户手动更改及停用/删除后不恢复、任务记忆版本依据、原生选目录、当前版本新建项目初始化与持久化，以及实际打包内容。涉及程序启动、测试及模型联调时，在执行计划中明确数据隔离、命令范围和现有授权是否覆盖；不因本次范围调整扩大启动或模型调用授权。

成本判断：文件导入和移动为中等改动，重点在写协调；项目记忆改造为中等偏高，重点在真实输入与确认来源；长期记忆为中等偏高，重点在用户编辑、检索边界和任务依据，优先复用现有 knowledge 模块。旧内容兼容已退出剩余验收范围，整体不重做 P1–P7。

### 11.3 集中审阅的六项安排（已获后续明确确认）
